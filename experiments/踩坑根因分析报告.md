# 踩坑根因分析报告

> 主题：三实验（信用卡欺诈 MLP / 肺炎 X 光 CNN / YOLOv8n 人员检测）在 Orange Pi AI Pro（昇腾 310B4）上的部署
> 平台：CANN 8.0.0 · driver 25.2.0 · Ubuntu 22.04 aarch64 · 板端 PyTorch 2.1.0 / Python 3.9
> 日期：2026-10-19　归档：`/opt/orangepi/`

---

## 0. 先给结论：18 个坑，归成 7 类根因

这一轮踩的坑不是随机分布的。把它们按「为什么会存在」分类后，可以看出一个清晰的模式：

| 类型 | 数量 | 本质 | 代表 |
|---|---|---|---|
| **① 环境漂移** | 3 | 工具的默认行为随版本静默改变，脚本没跟着变 | ONNX 权重外置、pyACL 常量、numpy API |
| **② 交付不完整** | 2 | 声明的产物清单 ≠ 真实产物清单 | 漏打包 `.onnx.data`、手册路径过期 |
| **③ 抽象层级错配** | 6 | 把 CLI 当 API、把高层封装当底层用 | 逐条起子进程、手写 pyACL 绑定、串行阻塞 |
| **④ 语义假设未校验** | 1 | 对数据含义的隐含假设没有验证 | 阈值 logit 差值 vs 概率 |
| **⑤ 硬件/驱动层** | 2 | 硬件能力或底层库的固有约束 | MIPI multiplanar、oneDNN matmul |
| **⑥ 宿主环境差异** | 3 | Windows 宿主的 shell/路径/进程语义与 Linux 不同 | MSYS 路径转换、kill 失效、bashrc |
| **⑦ 共享状态未保护** | 3 | 一个 shell 被多方同时使用，无同步 | 回显误判、sudo 抢读、并发串台 |

**一句话总结**：这 18 个坑里，真正属于"昇腾难用"的只有 2 个（⑤）。其余 16 个都是**工程与流程问题**——版本漂移、交付遗漏、抽象用错层级、宿主差异、共享状态。也就是说，换任何一块板子，这些坑一个都不会少。

## 1. 模型交付层

### 坑 1 · ONNX 引用的外部权重文件没随包交付（实验一、二）

**现象**

`atc --model=mlp_fraud.onnx` 直接失败，报 `Failed to get real path`。检查文件后发现反常的大小：

| 文件 | 实际大小 | 模型真实权重（fp32 估算） | 判断 |
|---|---|---|---|
| `exp1/mlp_fraud.onnx` | **6,673 B** | 4,033 参数 ≈ 15.8 KB | 权重不在里面 |
| `exp2/cnn_pneumonia_efficientnet_b0.onnx` | **658,670 B** | ~4.0M 参数 ≈ 15.3 MB | 权重不在里面 |
| `exp3/yolov8n.onnx` | 12,851,144 B | 3.2M 参数 ≈ 12.2 MB | **吻合，权重内联** |

**根因（关键发现）**

在 ONNX 二进制里直接 grep 出了答案：

```
exp1/mlp_fraud.onnx                        → 内含字符串 "mlp_fraud.onnx.data"
exp2/cnn_pneumonia_efficientnet_b0.onnx    → 内含 "cnn_pneumonia_efficientnet_b0.onnx.data"
exp3/yolov8n.onnx                          → 无
```

并且 exp1/exp2 的 ONNX 里还嵌入了这些 metadata：

```
pkg.torch.export.ExportedProgram.graph_signature
pkg.torch.onnx.fx_node
pkg.torch.onnx.name_scopes
pkg.torch.onnx.original_node_name
C:\Users\<you>\Desktop\...
C:\Users\<you>\AppData\Local\Python\pythoncore-3.14-6
2.14.0+
```

这几行把整条因果链坐实了：

1. 这两个模型是在 **Windows 本机**用 **PyTorch 2.14.0+ / Python 3.14** 导出的（路径与版本号残留在 metadata 里）。
2. `pkg.torch.export.ExportedProgram` 是 **PyTorch 新版 dynamo ONNX exporter** 的标志。PyTorch 2.9 起 `torch.onnx.export` 的 `dynamo` 参数默认为 `True`，即**默认已从旧的 TorchScript exporter 切到 dynamo exporter**。
3. 新 exporter 基于 `torch.export` 的 `ExportedProgram`，**默认把权重写成外部数据文件** `<模型名>.onnx.data`，`.onnx` 主文件只保留图结构和一个指向外文件的引用。
4. 导出脚本 `export_onnx_creditcard.py` / `export_onnx_pneumonia.py` 里只有一句 `torch.onnx.export(model, dummy, args.onnx_out, ...)`——**没有 `dynamo=False`**。脚本是按旧 exporter 的行为写的：那时只有一个产物文件。
5. 脚本的自检是 `onnx.checker.check_model` + `onnxruntime` 推理。这两步在**导出机上**都会通过，因为 `.onnx.data` 就躺在旁边。**自检全绿，但掩盖了"产物是两个文件"这个事实。**
6. 打包交付时按脚本声明的 `--onnx-out` 只收了 `.onnx`，`.onnx.data` 被漏掉。到了没有导出环境的板子上，引用断了。

**为什么实验三没事**

`yolov8n.onnx` 是通过 **ultralytics 8.4.178 的 `model.export()`** 导出的（文件内 producer 为 `Ultralytics`），走的是 ultralytics 自己的导出路径，不走 torch dynamo exporter，权重内联 → 一次编译通过。

**解决**

- 实验一：板端无法用 torch 重导（见坑 2），改用 `onnx.helper` **按 `.pt` 权重手工构图**，产出 `mlp_fraud_inline.onnx`（16 KB），并用 `onnx.reference.ReferenceEvaluator` 校验与 numpy 前向结果 **diff = 0**。
- 实验二：板端跑原脚本 `export_onnx_pneumonia.py` 重导，得 `cnn_inline.onnx`（16.0 MB，内联）。

**教训**

> 一个"导出成功 + 本地自检通过"的模型，**不等于一个可交付的模型**。
> 交付前必须校验：产物文件集合是否完整、脱离导出环境后能否独立加载。
> 凡是跨环境交付 ONNX，一律显式写 `dynamo=False`（或明确接受外置并一起打包），不要依赖默认值。

### 坑 2 · aarch64 上 `torch.onnx.export` 触发 oneDNN matmul 错误（实验一）

**现象**

板上重导实验一时报：`could not create a primitive descriptor for a matmul primitive`。

但单独的 `torch.nn.Linear(29,64)` 前向**正常**，手动 `torch.mm` 也正常，关掉 `torch.backends.mkldnn.enabled = False` 后**仍然失败**。

**根因**

板端是 **PyTorch 2.1.0 的 aarch64 构建**，其 oneDNN（mkldnn）后端在**特定 matmul 形状/内存布局组合**下无法创建 primitive descriptor。

- eager 模式下 `nn.Linear` 走的是另一条 kernel 选择路径，可能命中了 ARM 的 gemm 实现，所以单独调用没事；
- `torch.onnx.export` 走 **TorchScript tracing**，tracing 过程中会插入额外的 reshape/flatten/常量折叠（`do_constant_folding=True`）操作，产生**非标准内存布局**的 matmul，此时 oneDNN 找不到可用的 primitive descriptor 就报错；
- `torch.backends.mkldnn.enabled` 主要约束 conv 等算子，**管不到 matmul 的 oneDNN 派发路径**，所以关了没用。

这是 aarch64 wheel 与打包的 oneDNN 版本之间的兼容性缺陷，不是我们代码的错。

**解决**

不跟这个库硬碰。MLP 只有三层（29→64→32→1），结构完全已知，直接**绕开 torch 运行时**：用 `onnx.helper` 按 `.pt` 里的权重手工拼出 Gemm/Relu 图，再用 `ReferenceEvaluator` 与 numpy 前向对比验证（diff = 0）。产出 16 KB 内联 ONNX，ATC 一次通过。

**教训**

> 遇到底层库在特定形状上的缺陷，**先评估"绕过去"和"修好它"的成本比**。
> 结构已知的小模型，手写图 + 数值校验，比调试一个自己不维护的二进制依赖更快也更可控。

## 2. 工具链层

### 坑 3 · 手册里的 `set_env.sh` 路径不存在

**现象**

按手册执行 `source /usr/local/Ascend/ascend-toolkit/latest/setenv.sh`，文件不存在。

**根因**

两处都错了，是典型的**文档随版本漂移**：

| 手册写法 | 实际 |
|---|---|
| `.../latest/setenv.sh` | `.../ascend-toolkit/set_env.sh` |
| 文件名 `setenv.sh`（无下划线） | `set_env.sh`（有下划线） |

CANN 的目录布局在不同发行版/安装方式下不一致，`latest` 软链接的有无、脚本的命名和层级都会变。手册照抄了另一套布局。

**解决**

改成 `source /usr/local/Ascend/ascend-toolkit/set_env.sh`。

**教训**

> 手册路径当作**提示**而非事实。第一次到一台新机器上，先 `ls` 确认真实布局，把确认过的路径写进自己的脚本。

### 坑 4 · `ais_bench` 命令不在 PATH，且参数名与脚本不符

**现象**

`which ais_bench` 失败；但 `python3 -m ais_bench --help` 能跑。脚本里用的 `--output_size` / `--batch_size` 与当前版本参数名不一致。

**根因**

两个独立原因叠在一起：

1. **Python 包装了，但 console entry point 没注册**（或注册到了不在 PATH 的目录）。包体在 `/usr/local/miniconda3/lib/python3.9/site-packages/ais_bench/` 里，模块可 import，但 shell 找不到可执行入口。
2. **CLI 参数命名随版本变化**。旧版是 `--output_size` / `--batch_size`（下划线），新版改成了驼峰 `--outputSize` / `--batchSize`。作者按旧文档写的脚本，在新版本上参数不识别。

**解决**

建一个 wrapper 把模块入口暴露成命令：

```sh
# ~/exp/bin/ais_bench
#!/bin/sh
exec python3 -m ais_bench "$@"
```

`chmod +x` 后把 `~/exp/bin` 加入 PATH。

**教训**

> 判断一个工具"有没有装"，`which` 不是可靠依据——先试 `python3 -m <包>`。
> 命令行工具的**参数名属于 API 契约**，跨版本不保证稳定；脚本里硬编码参数名时，要锁定版本号。

### 坑 5 · `ais_bench 0.0.2` 的 `InferSession` 没有 `free_resource`

**现象**

推理结束释放资源时报 `AttributeError: 'InferSession' object has no attribute 'free_resource'`。

**根因**

`free_resource` 是较新版本才加入的方法。0.0.2 这个早期版本靠对象析构 / 进程退出来释放 ACL 资源，没有显式释放接口。调用方按新文档写的代码在旧包上跑必然失败。

**解决**

`try/except AttributeError` 兜底。进程退出时 ACL 会自行析构，不影响正确性。

**教训**

> 对**第三方对象的能力**做假设前先探测（`hasattr`），或者干脆用 try/except 包住"锦上添花"的清理动作——释放失败不应该让主流程崩掉。

### 坑 6 · `infer_yolov8_ascend.py` 的 pyACL 绑定与板上版本不兼容

**现象**

摄像头循环一启动就崩：`acl.RT_MEMCPY_HOST_TO_DEVICE` 不存在；`numpy_to_ptr` 也已废弃。

**根因**

这是**把 C/C++ 头文件里的常量名直接套到 Python 模块命名空间**造成的。

- ACL 的 C 头文件里常量叫 `ACL_MEMCPY_HOST_TO_DEVICE`，pyACL 的 Python 模块里可能是 `acl.RT_MEMCPY_HOST_TO_DEVICE`（旧）或 `ACL_MEMCPY_HOST_TO_DEVICE`（新），**不同 CANN 版本的 pyACL 命名空间不一致**；
- `numpy_to_ptr` 在新版 pyACL 里被 `acl.util.bytes_to_ptr` 取代。

作者把一套手写 pyACL 绑定（大概率按旧版 CANN 或按 C 示例写的）搬到了 CANN 8.0.0 上，命名对不上。

**解决**

不去逐个修它那套手写绑定（工程量与风险都不划算），改用**更高层且版本匹配的封装** `ais_bench.infer.interface.InferSession`——它把 ACL 初始化、内存拷贝、输入输出张量管理全部包掉了，只需 `session.infer([input])`。据此重写了 `cam_detect_yolo.py` 和 `cam_stream_server.py`。

**教训**

> 能用**随工具链一起发布的高层 API**，就不要手写底层绑定。
> 手写绑定等于自己维护一份与上游版本强耦合的契约；上游一升级，这份契约就断了。

## 3. 性能与架构层

### 坑 7 · `--all-test` 每条样本起一次 ais_bench 子进程

**现象**

原脚本 `infer_mlp_ascend.py --all-test` 的设计是：对测试集每条样本 `subprocess` 调用一次 `ais_bench`。56,962 条 → 按 1 s/条保守估算需 **约 16 小时**，而且慢到无法接受。

**根因**

三个层面的问题叠加：

1. **抽象层级错配**：把 `ais_bench` 当命令行工具循环调用，而不是当 Python API 用。CLI 每次启动都要付出：进程创建 + Python 解释器启动 + import ais_bench/ACL + **ACL 初始化 + OM 模型加载**。
2. **固定开销远大于实际计算**：实测 OM 加载 **1.24 s**，而单条推理只要 **0.207 ms**。加载开销是推理的 **约 6,000 倍**。也就是说 99.98% 的时间花在了重复加载模型上。
3. **测出来的延迟是假的**：每条的耗时里包含加载，得到的数字完全不反映 NPU 的真实推理性能。

**解决**

改用 `InferSession`：**只加载一次模型**，然后在 Python 里循环喂数据。

| | 原方案 | 新方案 |
|---|---|---|
| 模型加载次数 | 56,962 | **1** |
| 全量耗时 | ≈ 16 小时 | **12.7 秒** |
| 单条延迟 | 被加载时间淹没 | **0.207 ms**（p99 0.295） |
| 吞吐 | — | **4,497 条/秒** |

**教训**

> 看到"循环里启动外部进程"就要警觉：**固定开销 × N** 是性能杀手。
> 判断依据很简单——比较"单次调用的固定开销"和"单次调用的实际计算量"，如果前者远大于后者，就该把循环移进进程内。

### 坑 8 · MIPI 摄像头不支持 MJPG，取帧失败

**现象**

`infer_yolov8_ascend.py --device /dev/video0` 读不出帧。

**根因**

板载的 `/dev/video0`、`/dev/video1` 是 **MIPI CSI 摄像头经 ISP 后的节点**：

- `v4l2-ctl --list-formats` 列出的只有 NV12 / UYVY 等 **raw 格式**，没有 MJPG；
- 缓冲类型是 `V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE`（**multiplanar**），而 OpenCV 的 `CAP_V4L2` 默认请求 single-planar；
- 脚本强制设置 `CAP_PROP_FOURCC = MJPG`，设备不支持 → 格式协商失败；
- 此外 ISP pipeline 需要 `media-ctl` 配置链路与更高权限。

**UVC（USB）摄像头**则直接提供 MJPG/YUYV 的 single-planar 流，所以后来接入的 USB 摄像头被识别为 `/dev/video2`（`/dev/video3` 是 metadata 节点）后，一次就通了。

**解决**

接入 USB UVC 摄像头，改用 `/dev/video2`。

**教训**

> **设备节点存在 ≠ 能按你的方式读**。先 `v4l2-ctl --list-formats` 确认支持的像素格式与缓冲类型，再决定用哪条路径去读。
> 板载 MIPI 与 USB UVC 是两套完全不同的驱动模型，不能复用同一份采集代码。

### 坑 9 · 摄像头端到端只有 16 FPS，而 NPU 明明有 37.8 FPS 余量

**现象**

纯推理 26.4 ms（37.8 FPS），但端到端 62.5 ms（16.0 FPS）。

**根因**

单线程串行流水线，所有环节排在同一条时间线上：

```
cap.read()  ──→  letterbox  ──→  infer  ──→  解码  ──→  画框  ──→  JPEG 编码
  ~33 ms           ~2 ms          26.4 ms       ~1 ms      ~1 ms      ~10 ms
```

NPU 只占 26.4 / 62.5 = **42%**，其余 58% 是 Python 侧的采集等待、预处理和 720p JPEG 编码。摄像头出帧本身就要 ~33 ms（30 fps 上限），这一段时间里 NPU 是**空闲**的。

**解决（已缓解，未彻底优化）**

`cam_stream_server.py` 把「采集 → 推理 → 绘图 → 编码」放进**一个后台线程**持续跑，HTTP 线程只负责把最新一帧推给浏览器——这样至少避免了多个 HTTP 并发请求互相抢 NPU 会话。实测整环约 13.8 fps。

**教训**

> 加速卡利用率上不去时，先看是不是**前后处理在串行阻塞**。
> 标准解法：采集线程与推理线程解耦（用最新帧、丢弃积压帧），降低编码分辨率。预计可到 25–30 FPS。

## 4. 数值语义层

### 坑 10 · 阈值尺度：logit 差值 vs softmax 概率（**最容易翻车的一个**）

**现象**

手册说最佳阈值 **0.97**，对应 F1 0.840。直接把这个 0.97 套到板端 OM 的输出上：

| | 结果 |
|---|---|
| TP | **5** |
| FN | **385** |
| recall | **0.013** |
| F1 | **0.025** |

几乎全判成阴性，模型看起来"废了"。

**根因**

翻基线脚本 `eval_baseline.py`，它用的**不是概率**：

```python
# 基线用的判定分数
score = logits[1] - logits[0]     # 原始 logit 差值，无界、可以远大于 1
```

而板端 OM 输出后我按常规做法做了 `softmax`，得到的是**概率**（有界，0~1）。

两者是**完全不同的尺度**：

| 尺度 | 取值范围 | 0.97 意味着 |
|---|---|---|
| logit 差值 `logits[1]-logits[0]` | (−∞, +∞)，实测正例 p50 约 +2.5 | 一个**较宽松**的门槛 |
| softmax 概率 | (0, 1)，实测正例 p50 0.922、负例 p50 0.832 | 一个**极严苛**的门槛 |

同一个数字 0.97，在两个尺度上含义天差地别。softmax 后正例的中位数才 0.922，卡 0.97 等于只放行最极端的极少数样本。

**解决**

按基线**同一尺度**重算。把 softmax 概率反解成 logit 差值 `d = log(p / (1-p))`，再卡 0.97：

| | 基线 | 板端 OM |
|---|---|---|
| TP | — | 390 |
| FP | — | 151 |
| FN | — | 0 |
| TN | — | 83 |
| **F1 @0.97** | **0.8396** | **0.8378** |

**只差 2 张图，数值等价成立**。这才是"OM 与基线一致"的正确验证方式。

顺带把逐图得分落盘（`scores.npz`）后扫描，logit 尺度最佳 F1 为 **0.8735 @1.623**（等价 softmax 0.85）。

**教训**

> **阈值从来不是一个孤立的数字，它绑定着"分数的定义"。**
> 跨系统比对指标时，第一件事是确认两边的分数是不是在同一个尺度上——是 logit、logit 差值、sigmoid 概率还是 softmax 概率。
> 校准阈值时把逐样本得分落盘再扫描，比猜一个数字可靠得多。

## 5. 远程控制工程层

> 这一类是"我怎么控制板子"这一侧踩的坑，与模型无关，但占了总数的三分之一。

### 坑 11 · 终端回显导致命令结束判定失效

**现象**

命令执行了、退出码也对，但**输出内容丢失**；有时命令还没跑完就被判定为"已结束"。

**根因**

我用「发命令 → 发一个带唯一 marker 的 `echo` → 在输出流里找 marker」来判断命令结束。但交互式 shell 的 pty 默认开启**输入回显**：我写进去的 `echo __OPI_xxx__:$?` 这行**本身也被回显回输出流**，于是程序看到的第一个 marker 是回显的那一行，不是命令真正执行后的输出 → 提前判定结束，真正的输出还在路上。

**解决**

连接建立后立刻 `stty -echo` 关掉回显，并把结束判定改严（要求匹配 `marker:-?\d+` 的完整正则，而非子串）。

**教训**

> 通过 pty 与交互式程序对话时，**回显是最容易被忽略的污染源**。
> 凡是"往终端写、从终端读"的自动化，第一步先关回显。

---

### 坑 12 · 结束标记被 `sudo` 当成密码读走

**现象**

`sudo` 命令后出现 `Sorry, try again`，随后认证失败。

**根因**

我原本把**命令和 marker 一次性写入**：

```
cmd\n
echo __OPI_xxx__:$?\n     ← 两条同时进 stdin 缓冲区
```

`sudo` 在等待密码输入时，直接从 stdin 把**下一条**——即 marker 那行——当密码读了。密码错 → "Sorry, try again"；marker 也被消耗掉了，程序永远等不到它。

**解决**

改成**分阶段**：先发命令，监测输出流，确认**静默 0.6 秒**（说明命令真的停下来在等输入或已结束）后再发 marker。同时监测 `[sudo] password for` 提示并自动补密码。

**教训**

> 与交互式程序对话，**不能假设"写进去的东西会按顺序被正确的人读到"**。
> 只要目标程序可能读 stdin，就必须先确认它当前的输入状态再决定下一步写什么。

---

### 坑 13 · 持久 shell 并发串台

**现象**

多个请求同时到达时输出互相污染；严重时会有一个 handler 永久阻塞在锁上，后续请求全部堵死，桥接进程假死。

**根因**

我用 `ThreadingTCPServer`（多线程）+ **一个共享的持久 shell**。两个请求同时发命令时，两边的输出流混在一起，谁也分不清哪段是自己的。加了串行锁之后又暴露第二个问题：客户端超时断开后，服务端的 handler 还阻塞在锁上等一个永远不会来的响应 → 队列堵死。

**解决**

1. 加全局串行锁，保证同一时刻只有一个命令在 shell 里跑；
2. **给锁等待加超时上限**，超时直接返回错误而不是无限等；
3. 更根本的调整：**长任务不再占用持久 shell**，改成板端 `nohup` 后台跑 + 轮询日志；
4. 最终直接改用**每条命令独立 SSH 通道**（`opi_exec.py`），彻底消除共享状态。

**教训**

> 共享可变资源（一个 shell、一个 NPU 会话）必须配同步，而同步必须配**超时**——否则一次客户端异常就会永久拖死服务端。
> 更进一步：**能无状态就不要有状态**。独立通道虽然每条都要重新登录，但它不会积累脏状态，可靠性远胜持久会话。

### 坑 14 · Git Bash 把远端路径做了 MSYS 转换

**现象**

`sftp push` 的远端路径明明写的是 `/home/HwHiAiUser/exp/exp1`，文件却没传到板子上。

**根因**

Git Bash 基于 MSYS2 runtime，它会把**看起来像 POSIX 路径的命令行参数**自动转换成 Windows 路径。`/home` 在 MSYS 里挂载到 Git 安装目录下，于是：

```
/home/HwHiAiUser/exp/exp1
  → D:/.../PortableGit/home/HwHiAiUser/exp/exp1
```

这个转换发生在**参数传给 Python 之前**，Python 拿到的是一个 Windows 风格的路径字符串，SFTP 服务端自然按这个名字建目录/写文件。

**解决**

改用 **PowerShell** 调用 Python（原生 Windows 进程，不存在 MSYS 转换）。或者在 Git Bash 里设 `MSYS_NO_PATHCONV=1`。

**教训**

> 在 Git Bash / MSYS / Cygwin 里执行**任何带路径参数的跨系统命令**都要警惕路径转换。
> 涉及远程路径、URL、注册表路径时，优先用 PowerShell。

### 坑 15 · Git Bash 的 `kill` 杀不掉 Windows 进程

**现象**

`kill <pid>` 之后，桥接进程依然存活，端口仍被占用。

**根因**

Git Bash 的 `kill` 是 MSYS 自己的实现，只能可靠地向 **MSYS 进程树**内的进程发信号。而桥接进程是由 **Windows 原生 Python** 启动的，不在 MSYS 进程树里，信号处理不可靠。

**解决**

用 PowerShell：

```powershell
Stop-Process -Id <pid> -Force
```

**教训**

> 在 Windows 上管理进程，**用什么启动的就用什么管理**。跨子系统（MSYS ↔ 原生 Windows）发信号是不可靠的。

### 坑 16 · `bash -lc` 不读 `~/.bashrc`，CANN 与 miniconda 环境丢失

**现象**

同一条命令，交互式执行正常，通过 SSH 非交互执行就报"找不到 atc"或"找不到 python 包"。

**根因**

两个独立原因：

1. **`bash -l` 是 login shell**，它读 `/etc/profile`、`~/.bash_profile`、`~/.profile`，**不读 `~/.bashrc`**。而 CANN 的 `set_env.sh` 和 miniconda 的 PATH 恰恰是写在 `~/.bashrc` 里的（这台机器的 `~/.bash_profile` 没有 source 它）。
2. `python3` 解析到了**系统解释器**（`/usr/bin/python3`），而不是 miniconda 的 Python 3.9——后者才是装了 torch/torchvision/acl 的那个。

**解决**

在执行器里显式拼装环境：

```sh
source /usr/local/Ascend/ascend-toolkit/set_env.sh
export PATH=/usr/local/miniconda3/bin:$HOME/exp/bin:$PATH
export TE_PARALLEL_COMPILER=1 MAX_COMPILE_CORE_NUMBER=1
```

**教训**

> 非交互执行**永远不要依赖 shell 的启动文件**。把需要的环境变量显式写进执行脚本，环境才是可复现的。

### 坑 17 · SFTP 对单文件也建了同名目录

**现象**

推送单个文件时失败：`sftp.put(local, remote)` 报文件已存在/无法写入。

**根因**

我自己写的 `push()` 里，为了支持递归上传，先调用了 `mkdir_p(sftp, remote)` 把**远端路径当目录**逐层创建。当 `local` 是个**文件**时，`remote` 也被当成目录建了出来，于是 `put` 到同名路径时目标已是个目录 → 写不进去。

**解决**

`push()` 开头先判断：若 `local` 是文件，跳过 `mkdir_p`，直接 `put`。

**教训**

> 递归工具里的"创建父目录"逻辑，必须区分**目标是文件还是目录**。这一类 bug 在"传目录"的测试里永远发现不了，只有传单文件时才暴露。

### 坑 18 · `np.trapezoid` 不存在

**现象**

计算 AUPRC 时 `AttributeError: module 'numpy' has no attribute 'trapezoid'`。

**根因**

`np.trapezoid` 是 **NumPy 2.0** 才引入的名字；板端 numpy 是 1.x，只有旧名 `np.trapz`。这是库在 2.0 时的重命名（旧名被标记 deprecated 但未立即移除）。

**解决**

改用 `np.trapz`（在 numpy 1.x 和 2.x 里都可用）。

**教训**

> 写跨环境运行的脚本时，**优先用两个版本都支持的 API 名**，或者在入口处做一次版本探测。开发机与部署机的库版本往往不一致。

## 7. 防御清单：下次怎么提前发现

按执行顺序排列，每一条都对应上面具体地踩过的坑：

**交付前（在导出机上）**

- [ ] 列出导出的**全部产物文件**（`ls -la` 对比前后目录），确认 `.onnx` 之外没有 `.onnx.data` 之类的伴生文件
- [ ] `torch.onnx.export` 显式写 `dynamo=False`，不要依赖默认
- [ ] 脱离导出环境验证：把产物**拷到干净目录/另一台机器**再加载一次
- [ ] 记录导出环境的 torch / Python / OS 版本，与产物一起归档

**到新机器上（第一件事）**

- [ ] `ls` 确认 CANN 脚本的真实路径，别信手册
- [ ] `which` 找不到工具时，试 `python3 -m <包>`
- [ ] `v4l2-ctl --list-formats` 确认摄像头支持的格式与缓冲类型
- [ ] 显式 source 环境变量，**不依赖 `.bashrc`**

**写推理代码时**

- [ ] 优先用随工具链发布的高层 API（`InferSession`），不手写底层绑定
- [ ] 循环推理时**模型只加载一次**
- [ ] 比较固定开销与实际计算量，判断要不要把循环移进进程
- [ ] 第三方对象的"锦上添花"方法（如资源释放）用 `try/except` 包住

**比对指标时**

- [ ] 先确认两边的分数**在同一尺度**（logit / logit 差值 / sigmoid / softmax）
- [ ] 把逐样本得分落盘，扫描阈值，而不是直接套用文档里的数字

**跨系统操作（Windows → Linux）**

- [ ] 涉及远端路径的命令用 PowerShell，不用 Git Bash
- [ ] 杀进程用 PowerShell `Stop-Process`，不用 Git Bash 的 `kill`
- [ ] 与交互式程序对话前先 `stty -echo`；可能读 stdin 的命令分阶段发送
- [ ] 共享资源加锁，**锁必须有超时**；长任务改后台 + 轮询，不占持久会话

## 8. 一句话总结

这 18 个坑里，只有一个（MIPI 摄像头）是硬件真不具备能力，一个（oneDNN matmul）是底层库的缺陷，**其余 16 个全都是"本可以提前发现"的工程问题**——版本默认值变了、产物漏打包了、参数名改了、分数尺度没对齐、宿主 shell 语义不同、共享状态没保护。

它们的共同点是：**每一步单独看都是"应该没问题"的，问题只在不同环节的交界处才暴露**。所以防御的重点不在某个具体技术，而在**交接点上的显式校验**——产物清单、路径、版本、尺度、环境，凡是跨边界传递的东西，都要验一遍而不是默认它对。
