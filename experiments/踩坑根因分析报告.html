Post-mortem · Root Cause Analysis

踩坑根因分析报告

三个实验（信用卡欺诈 MLP / 肺炎 X 光 CNN / YOLOv8n 人员检测）在 Orange Pi AI Pro 上完成昇腾端部署， 全程共踩 18 个坑。本报告回答两件事：为什么会出现这些问题，以及当时是怎么解决的。

板卡 Orange Pi AI Pro · 昇腾 310B4 CANN 8.0.0 · driver 25.2.0 板端 Ubuntu 22.04 aarch64 · PyTorch 2.1.0 · Python 3.9 导出机 Windows · PyTorch 2.14.0 · Python 3.14 日期 2026-10-19
1

先给结论：18 个坑归成 7 类根因

这些坑不是随机分布的。按「为什么会存在」分类后，模式非常清楚—— 真正属于昇腾平台自身难度的只有 2 个（11%），其余 16 个全是通用工程问题。

① 环境漂移3 个

工具的默认行为随版本静默改变，脚本没跟着变。

ONNX 权重外置 · pyACL 常量 · numpy API 改名
② 交付不完整2 个

声明的产物清单 ≠ 真实产物清单。

漏打包 .onnx.data · 手册路径过期
③ 抽象层级错配6 个

把 CLI 当 API 用、把高层封装当底层手写。

逐条起子进程 · 手写 pyACL 绑定 · 串行阻塞
④ 语义假设未校验1 个

对数据含义的隐含假设没有验证。

阈值 logit 差值 vs softmax 概率
⑤ 硬件 / 驱动层2 个

硬件能力或底层库的固有约束，绕不开只能适配。

MIPI multiplanar · oneDNN matmul 缺陷
⑥ 宿主环境差异3 个

Windows 宿主的 shell / 路径 / 进程语义与 Linux 不同。

MSYS 路径转换 · kill 失效 · bashrc 不加载
⑦ 共享状态未保护3 个

一个 shell 被多方同时使用，却没有同步机制。

回显误判 · sudo 抢读 · 并发串台
一句话总结：换 RK3588、换 Jetson、换任何一块边缘板子，这 18 个坑里有 16 个会原样出现。 它们不是「昇腾难用」，而是工程与流程问题——版本漂移、交付遗漏、抽象用错层级、宿主差异、共享状态。
2

最有价值的一个发现：ONNX 权重为什么会外置

这不只是「打包漏了个文件」。在 ONNX 二进制里 grep 出的字符串，把整条因果链完整还原了出来—— 它是一个工具默认行为静默变更导致的连锁反应。

3

模型交付层

模型从导出机到板子这一段的问题。根因是「产物是什么」这件事被想当然了。

坑 1ONNX 引用的外部权重文件没随包交付（实验一、二） ①② 环境漂移 / 交付不完整
现象

atc --model=mlp_fraud.onnx 直接失败：Failed to get real path。

根因

四个环节依次失守：

1. 版本升级改了默认值。 PyTorch 2.9 起 torch.onnx.export 的 dynamo 参数默认为 True，从旧的 TorchScript exporter 切到了 dynamo exporter。导出机是 torch 2.14.0，早已切换。

2. 新 exporter 默认外置权重。 它基于 torch.export 的 ExportedProgram，默认把权重写成 <模型名>.onnx.data，主文件只留图结构和引用。

3. 脚本没跟上。 脚本里只有一句 torch.onnx.export(model, dummy, out, ...)，没写 dynamo=False——它按旧 exporter「只有一个产物」的行为写的。

4. 自检掩盖了问题。 onnx.checker.check_model + onnxruntime 推理在导出机上全部通过，因为 .onnx.data 就躺在旁边。于是打包时只收了 .onnx。

解决

实验二：板端跑原脚本重导 → cnn_inline.onnx（16.0 MB，内联）。

实验一：板端无法用 torch 重导（见坑 2），改用 onnx.helper 按 .pt 权重手工构图 → mlp_fraud_inline.onnx（16 KB），并用 ReferenceEvaluator 校验与 numpy 前向 diff = 0。

教训

一个「导出成功 + 本地自检通过」的模型，不等于一个可交付的模型。交付前必须校验产物文件集合是否完整、脱离导出环境后能否独立加载。跨环境交付 ONNX 一律显式写 dynamo=False，别依赖默认值。

坑 2aarch64 上 torch.onnx.export 触发 oneDNN matmul 错误 ⑤ 硬件 / 驱动层
现象

报 could not create a primitive descriptor for a matmul primitive。

但单独 nn.Linear(29,64) 前向正常，手动 torch.mm 正常，torch.backends.mkldnn.enabled=False 后仍然失败。

根因

板端是 PyTorch 2.1.0 的 aarch64 构建，其 oneDNN 后端在特定 matmul 形状 / 内存布局组合下无法创建 primitive descriptor。

为什么单独调用没事： eager 模式下 nn.Linear 走另一条 kernel 选择路径，可能命中 ARM 的 gemm 实现。

为什么 export 时炸： torch.onnx.export 走 TorchScript tracing，过程中会插入 reshape / flatten / 常量折叠（do_constant_folding=True），产生非标准内存布局的 matmul，oneDNN 找不到可用 descriptor 就报错。

为什么关 mkldnn 没用： torch.backends.mkldnn.enabled 主要约束 conv 等算子，管不到 matmul 的 oneDNN 派发路径。

解决

不跟库硬碰。MLP 只有三层（29→64→32→1）、结构完全已知，直接绕开 torch 运行时：用 onnx.helper 按权重手工拼 Gemm / Relu 图，再用 ReferenceEvaluator 与 numpy 前向对比（diff = 0）。

教训

遇到底层库在特定形状上的缺陷，先比较「绕过去」和「修好它」的成本。结构已知的小模型，手写图 + 数值校验比调试一个自己不维护的二进制依赖更快、更可控。

4

工具链层

CANN / ais_bench / pyACL 的使用问题。共同点是对着旧版本的印象写代码。

坑 3手册里的 set_env.sh 路径不存在 ② 交付不完整
现象

按手册 source /usr/local/Ascend/ascend-toolkit/latest/setenv.sh，文件不存在。

根因

两处都错，是典型的文档随版本漂移：路径层级上 latest/setenv.sh 实际是 ascend-toolkit/set_env.sh；文件名上 setenv.sh（无下划线）实际是 set_env.sh（有下划线）。CANN 的目录布局在不同发行版 / 安装方式下不一致，手册照抄了另一套。

解决

改为 source /usr/local/Ascend/ascend-toolkit/set_env.sh。

教训

手册路径当作提示而非事实。到新机器上先 ls 确认真实布局，把确认过的路径写进自己的脚本。

坑 4ais_bench 不在 PATH，且参数名与脚本不符 ③ 抽象层级错配
现象

which ais_bench 失败，但 python3 -m ais_bench --help 能跑；脚本里的 --output_size / --batch_size 不被识别。

根因

两个独立原因叠在一起：

1. 包装了但没注册入口。 包体在 site-packages/ais_bench/ 里，模块可 import，但 console entry point 没注册（或注册到了不在 PATH 的目录），shell 找不到可执行命令。

2. CLI 参数名随版本变化。 旧版用下划线 --output_size，新版改成驼峰 --outputSize。作者按旧文档写的脚本。

解决

建 wrapper 把模块入口暴露成命令：

#!/bin/sh
# ~/exp/bin/ais_bench
exec python3 -m ais_bench "$@"

chmod +x 后把 ~/exp/bin 加入 PATH。

教训

判断工具「有没有装」，which 不是可靠依据——先试 python3 -m <包>。命令行工具的参数名属于 API 契约，跨版本不保证稳定。

坑 5ais_bench 0.0.2 的 InferSession 没有 free_resource ③ 抽象层级错配
现象

释放资源时报 AttributeError: 'InferSession' object has no attribute 'free_resource'。

根因

free_resource 是较新版本才加的方法。0.0.2 这个早期版本靠对象析构 / 进程退出释放 ACL 资源，没有显式释放接口。调用方按新文档写代码，跑在旧包上必然失败。

解决

try/except AttributeError 兜底。进程退出时 ACL 会自行析构，不影响正确性。

教训

对第三方对象的能力做假设前先探测（hasattr），或用 try/except 包住「锦上添花」的清理动作——释放失败不应该让主流程崩掉。

坑 6手写 pyACL 绑定与板上 CANN 版本不兼容 ①③ 环境漂移 / 抽象错配
现象

摄像头循环一启动就崩：acl.RT_MEMCPY_HOST_TO_DEVICE 不存在；numpy_to_ptr 已废弃。

根因

本质是把 C/C++ 头文件里的常量名直接套到 Python 模块命名空间上。

ACL 的 C 头文件里常量叫 ACL_MEMCPY_HOST_TO_DEVICE；pyACL 的 Python 模块里可能是 acl.RT_MEMCPY_HOST_TO_DEVICE（旧）或 ACL_MEMCPY_HOST_TO_DEVICE（新）——不同 CANN 版本的 pyACL 命名空间不一致。同理 numpy_to_ptr 在新版被 acl.util.bytes_to_ptr 取代。

作者把一套手写绑定（大概率按旧版 CANN 或按 C 示例写的）搬到了 CANN 8.0.0 上，命名对不上。

解决

不逐个修它那套手写绑定（工程量与风险都不划算），改用更高层且版本匹配的封装 ais_bench.infer.interface.InferSession——它把 ACL 初始化、内存拷贝、输入输出张量管理全部包掉，只需 session.infer([x])。据此重写了 cam_detect_yolo.py 与 cam_stream_server.py。

教训

能用随工具链一起发布的高层 API，就不要手写底层绑定。手写绑定等于自己维护一份与上游版本强耦合的契约；上游一升级，这份契约就断了。

5

性能与架构层

模型能跑之后，跑得对不对、快不快的问题。

坑 7--all-test 每条样本起一次 ais_bench 子进程 ③ 抽象层级错配
现象

原脚本对 56,962 条样本逐条 subprocess 调用 ais_bench，按 1 s/条保守估算需 约 16 小时。

根因

1. 抽象层级错配。 把 ais_bench 当命令行工具循环调用，而不是当 Python API 用。CLI 每次启动都要付出：进程创建 + 解释器启动 + import + ACL 初始化 + OM 加载。

2. 固定开销远大于实际计算。 实测 OM 加载 1.24 s，而单条推理只要 0.207 ms——加载开销是推理的 约 6,000 倍，99.98% 的时间花在重复加载上。

3. 测出的延迟是假的。 每条耗时含加载，完全不反映 NPU 真实性能。

解决

改用 InferSession，只加载一次模型，在 Python 里循环喂数据：

原方案新方案
模型加载次数56,9621
全量耗时≈ 16 小时12.7 秒
单条延迟被加载淹没0.207 ms
吞吐—4,497 条/秒
教训

看到「循环里启动外部进程」就要警觉：固定开销 × N 是性能杀手。判断依据很简单——比较单次调用的固定开销与实际计算量，前者远大于后者时，就把循环移进进程内。

坑 8MIPI 摄像头不支持 MJPG，取帧失败 ⑤ 硬件 / 驱动层
现象

--device /dev/video0 读不出帧。

根因

板载 /dev/video0、/dev/video1 是 MIPI CSI 摄像头经 ISP 后的节点，与 USB UVC 是两套完全不同的驱动模型：

· v4l2-ctl --list-formats 只列出 NV12 / UYVY 等 raw 格式，没有 MJPG；
· 缓冲类型是 V4L2_BUF_TYPE_VIDEO_CAPTURE_MPLANE（multiplanar），而 OpenCV 的 CAP_V4L2 默认请求 single-planar；
· 脚本强制设 CAP_PROP_FOURCC = MJPG，设备不支持 → 格式协商失败；
· 此外 ISP pipeline 需 media-ctl 配置链路与更高权限。

解决

接入 USB UVC 摄像头，识别为 /dev/video2（/dev/video3 是 metadata 节点），一次通过。

教训

设备节点存在 ≠ 能按你的方式读。 先 v4l2-ctl --list-formats 确认像素格式与缓冲类型，再决定采集路径。

坑 9摄像头端到端只有 16 FPS，而 NPU 有 37.8 FPS 余量 ③ 抽象层级错配
现象

纯推理 26.4 ms（37.8 FPS），端到端却 62.5 ms（16.0 FPS）。

根因

单线程串行流水线，所有环节排在同一条时间线上：

cap.read()  → letterbox → infer → 解码 → 画框 → JPEG 编码
  ~33 ms        ~2 ms      26.4 ms   ~1 ms   ~1 ms    ~10 ms
                            ↑ NPU 只占 26.4 / 62.5 = 42%

其余 58% 是 Python 侧的采集等待、预处理和 720p JPEG 编码。摄像头出帧本身就要 ~33 ms（30 fps 上限），这段时间里 NPU 是空闲的。

解决

cam_stream_server.py 把「采集 → 推理 → 绘图 → 编码」放进一个后台线程持续跑，HTTP 线程只推最新帧——至少避免了多个 HTTP 并发请求互相抢 NPU 会话。实测整环约 13.8 fps。

进一步优化方向：采集线程与推理线程解耦（用最新帧、丢弃积压帧）+ 降低编码分辨率，预计可到 25–30 FPS。

教训

加速卡利用率上不去时，先看是不是前后处理在串行阻塞。NPU 的算力指标（37.8 FPS）和端到端指标（16 FPS）之间，差的全是 CPU 侧开销。

数值语义层

只有一个坑，但它是最容易翻车的一个——因为它不会报错，只会给出一个「看起来模型废了」的错误结论。

坑 10阈值尺度：logit 差值 vs softmax 概率 ④ 语义假设未校验
现象

手册说最佳阈值 0.97，对应 F1 0.840。直接套到板端 OM 输出上：

TPFNrecallF1
5385 0.0130.025

几乎全判成阴性，模型看起来「废了」。

根因

翻基线脚本 eval_baseline.py，它用的不是概率：

score = logits[1] - logits[0]   # 原始 logit 差值，无界、可远大于 1

而我在板端按常规做法做了 softmax，得到的是概率（有界 0~1）。两者是完全不同的尺度：

尺度取值范围0.97 意味着
logit 差值 logits[1]-logits[0](−∞, +∞)，实测正例 p50 ≈ +2.5一个较宽松的门槛
softmax 概率(0, 1)，实测正例 p50 0.922 / 负例 0.832一个极严苛的门槛

同一个数字 0.97，在两个尺度上含义天差地别。softmax 后正例中位数才 0.922，卡 0.97 等于只放行最极端的极少数样本。

解决

按基线同一尺度重算：把 softmax 概率反解成 logit 差值 d = log(p / (1-p))，再卡 0.97：

TPFPFNTNF1 @0.97
基线————0.8396
板端 OM3901510830.8378

只差 2 张图，数值等价成立。这才是「OM 与基线一致」的正确验证方式。顺带把逐图得分落盘（scores.npz）后扫描，logit 尺度最佳 F1 为 0.8735 @1.623（等价 softmax 0.85）。

教训

阈值从来不是一个孤立的数字，它绑定着「分数的定义」。 跨系统比对指标时，第一件事是确认两边的分数是否在同一尺度——是 logit、logit 差值、sigmoid 概率还是 softmax 概率。校准阈值时把逐样本得分落盘再扫描，比猜一个数字可靠得多。

7

远程控制工程层

「我怎么控制板子」这一侧踩的坑，与模型无关，但占了总数的三分之一。

坑 11终端回显导致命令结束判定失效 ⑦ 共享状态未保护
现象

命令执行了、退出码也对，但输出内容丢失；有时命令还没跑完就被判定为「已结束」。

根因

我用「发命令 → 发一个带唯一 marker 的 echo → 在输出流里找 marker」来判断结束。但交互式 shell 的 pty 默认开启输入回显：写进去的 echo __OPI_xxx__:$? 这行本身也被回显回输出流。程序看到的第一个 marker 是回显的那一行，不是命令真正执行后的输出 → 提前判定结束。

解决

连接建立后立刻 stty -echo 关掉回显，并把结束判定改严（要求匹配 marker:-?\d+ 的完整正则，而非子串匹配）。

教训

通过 pty 与交互式程序对话时，回显是最容易被忽略的污染源。凡是「往终端写、从终端读」的自动化，第一步先关回显。

坑 12结束标记被 sudo 当成密码读走 ⑦ 共享状态未保护
现象

sudo 命令后出现 Sorry, try again，随后认证失败。

根因

我原本把命令和 marker 一次性写入：

cmd\n
echo __OPI_xxx__:$?\n     ← 两条同时进 stdin 缓冲区

sudo 等待密码输入时，直接从 stdin 把下一条——即 marker 那行——当密码读了。密码错 → Sorry, try again；marker 也被消耗掉，程序永远等不到它。

解决

改成分阶段：先发命令，监测输出流，确认静默 0.6 秒（说明命令真的停下来在等输入或已结束）后再发 marker；同时监测 [sudo] password for 提示并自动补密码。

教训

与交互式程序对话，不能假设「写进去的东西会按顺序被正确的人读到」。只要目标程序可能读 stdin，就必须先确认它当前的输入状态再决定写什么。

坑 13持久 shell 并发串台，桥接进程假死 ⑦ 共享状态未保护
现象

多个请求同时到达时输出互相污染；严重时一个 handler 永久阻塞在锁上，后续请求全部堵死。

根因

第一层： ThreadingTCPServer（多线程）+ 一个共享的持久 shell。两个请求同时发命令时输出流混在一起，分不清哪段是谁的。

第二层（加锁后暴露）： 客户端超时断开后，服务端 handler 仍阻塞在锁上等一个永远不会来的响应 → 队列堵死。

解决

1. 加全局串行锁，保证同一时刻只有一个命令在 shell 里跑；
2. 给锁等待加超时上限，超时直接返回错误而不是无限等；
3. 长任务不再占用持久 shell，改成板端 nohup 后台跑 + 轮询日志；
4. 最终改用每条命令独立 SSH 通道（opi_exec.py），彻底消除共享状态。

教训

共享可变资源必须配同步，而同步必须配超时——否则一次客户端异常就会永久拖死服务端。更进一步：能无状态就不要有状态。独立通道虽每条都要重新登录，但不积累脏状态，可靠性远胜持久会话。

坑 14Git Bash 把远端路径做了 MSYS 转换 ⑥ 宿主环境差异
现象

远端路径明明写的 /home/HwHiAiUser/exp/exp1，文件却没传到板子上。

根因

Git Bash 基于 MSYS2 runtime，会把看起来像 POSIX 路径的命令行参数自动转成 Windows 路径。而 /home 在 MSYS 里挂载到 Git 安装目录下：

/home/HwHiAiUser/exp/exp1
  → D:/.../PortableGit/home/HwHiAiUser/exp/exp1

转换发生在参数传给 Python 之前，Python 拿到的是 Windows 风格路径，SFTP 服务端自然按这个名字建目录。

解决

改用 PowerShell 调用 Python（原生 Windows 进程，不存在 MSYS 转换）。或在 Git Bash 里设 MSYS_NO_PATHCONV=1。

教训

在 Git Bash / MSYS / Cygwin 里执行任何带路径参数的跨系统命令都要警惕。涉及远程路径、URL、注册表路径时优先用 PowerShell。

坑 15Git Bash 的 kill 杀不掉 Windows 进程 ⑥ 宿主环境差异
现象

kill <pid> 之后桥接进程依然存活，端口仍被占用。

根因

Git Bash 的 kill 是 MSYS 自己的实现，只能可靠地向 MSYS 进程树内的进程发信号。桥接进程由 Windows 原生 Python 启动，不在该进程树里，信号处理不可靠。

解决

用 PowerShell：Stop-Process -Id <pid> -Force

教训

在 Windows 上管理进程，用什么启动的就用什么管理。跨子系统（MSYS ↔ 原生 Windows）发信号不可靠。

坑 16bash -lc 不读 ~/.bashrc，CANN 与 miniconda 环境丢失 ⑥ 宿主环境差异
现象

同一条命令交互式执行正常，通过 SSH 非交互执行就报「找不到 atc」或「找不到 python 包」。

根因

1. bash -l 是 login shell，读 /etc/profile、~/.bash_profile、~/.profile，不读 ~/.bashrc。而 CANN 的 set_env.sh 和 miniconda 的 PATH 恰恰写在 .bashrc 里（这台机器的 .bash_profile 没有 source 它）。

2. python3 解析到了系统解释器 /usr/bin/python3，而不是 miniconda 的 Python 3.9——后者才是装了 torch / torchvision / acl 的那个。

解决

在执行器里显式拼装环境：

source /usr/local/Ascend/ascend-toolkit/set_env.sh
export PATH=/usr/local/miniconda3/bin:$HOME/exp/bin:$PATH
export TE_PARALLEL_COMPILER=1 MAX_COMPILE_CORE_NUMBER=1
教训

非交互执行永远不要依赖 shell 启动文件。把需要的环境变量显式写进执行脚本，环境才是可复现的。

坑 17SFTP 对单文件也建了同名目录 ③ 抽象层级错配
现象

推送单个文件时 sftp.put(local, remote) 失败，报文件已存在 / 无法写入。

根因

自己写的 push() 为了支持递归上传，先调用 mkdir_p(sftp, remote) 把远端路径当目录逐层创建。当 local 是个文件时，remote 也被当成目录建了出来，于是 put 到同名路径时目标已是个目录 → 写不进去。

解决

push() 开头先判断：若 local 是文件，跳过 mkdir_p，直接 put。

教训

递归工具里的「创建父目录」逻辑必须区分目标是文件还是目录。这类 bug 在「传目录」的测试里永远发现不了，只有传单文件时才暴露。

坑 18np.trapezoid 不存在 ① 环境漂移
现象

计算 AUPRC 时 AttributeError: module 'numpy' has no attribute 'trapezoid'。

根因

np.trapezoid 是 NumPy 2.0 才引入的名字；板端 numpy 是 1.x，只有旧名 np.trapz。这是库在 2.0 时的重命名（旧名被标记 deprecated 但未立即移除）。

解决

改用 np.trapz（在 numpy 1.x 和 2.x 里都可用）。

教训

写跨环境脚本时优先用两个版本都支持的 API 名，或在入口处做一次版本探测。开发机与部署机的库版本往往不一致。

防御清单：下次怎么提前发现

按执行顺序排列，每一条都对应上面具体踩过的坑。

交付前（在导出机上）

  • 列出导出的全部产物文件（对比前后目录），确认 .onnx 之外没有 .onnx.data 之类伴生文件
  • torch.onnx.export 显式写 dynamo=False，不要依赖默认值
  • 脱离导出环境验证：把产物拷到干净目录 / 另一台机器再加载一次
  • 记录导出环境的 torch / Python / OS 版本，与产物一起归档

到新机器上（第一件事）

  • ls 确认 CANN 脚本真实路径，别信手册
  • which 找不到工具时，试 python3 -m <包>
  • v4l2-ctl --list-formats 确认摄像头支持的格式与缓冲类型
  • 显式 source 环境变量，不依赖 .bashrc

写推理代码时

  • 优先用随工具链发布的高层 API（InferSession），不手写底层绑定
  • 循环推理时模型只加载一次
  • 比较固定开销与实际计算量，判断要不要把循环移进进程
  • 第三方对象的「锦上添花」方法（如资源释放）用 try/except 包住

比对指标时

  • 先确认两边的分数在同一尺度（logit / logit 差值 / sigmoid / softmax）
  • 把逐样本得分落盘，扫描阈值，而不是直接套用文档里的数字

跨系统操作（Windows → Linux）

  • 涉及远端路径的命令用 PowerShell，不用 Git Bash
  • 杀进程用 Stop-Process，不用 Git Bash 的 kill
  • 与交互式程序对话前先 stty -echo；可能读 stdin 的命令分阶段发送
  • 共享资源加锁，锁必须有超时；长任务改后台 + 轮询，不占持久会话
最后一层观察。 这 18 个坑里，只有一个（MIPI 摄像头）是硬件真不具备能力，一个（oneDNN matmul）是底层库缺陷， 其余 16 个全都是「本可以提前发现」的工程问题——版本默认值变了、产物漏打包了、参数名改了、分数尺度没对齐、宿主 shell 语义不同、共享状态没保护。

它们的共同点是：每一步单独看都是「应该没问题」的，问题只在不同环节的交界处才暴露。 所以防御的重点不在某个具体技术，而在交接点上的显式校验——产物清单、路径、版本、尺度、环境， 凡是跨边界传递的东西，都要验一遍而不是默认它对。
