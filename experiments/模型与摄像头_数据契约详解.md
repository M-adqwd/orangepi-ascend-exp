# 模型与摄像头：数据契约详解

> 面向学习与研究。所有数值取自 Orange Pi AI Pro（Ascend 310B4）实测，不是通用估算。
> 对应代码：`~/exp/exp3/cam_stream_server.py` + `utils/preprocess.py` + `utils/yolov8_decode.py`

---

## 0. 一句话说清关系

**摄像头和模型之间没有任何物理连接，它们靠一段"数据契约"代码接起来。**

```
摄像头：我只能给你 1280×720×3 的 uint8 像素，BGR 顺序，要不要随你
   ↓
中间层：我负责把它变成你要的样子（这是唯一需要你写代码的地方）
   ↓
模型：  我只认 1×3×640×640 的 float32，RGB 顺序，值域 [0,1]，否则我给的答案不作数
```

模型不知道有摄像头这回事，摄像头也不知道有模型这回事。它们各自遵守自己的格式，中间那几十行预处理代码是唯一的桥梁。

**这个认知最重要**，因为桥搭错任何一步，模型照样能跑出结果——不报错、不崩，只是结果是错的。这是这类系统最隐蔽的故障类型。

## 1. 五阶段总表

| 阶段 | 数据形状 | dtype | 大小 | 谁在干活 |
|---|---|---|---|---|
| ① 采集 | `1280 × 720 × 3` | uint8 | 2.64 MiB | 内核 V4L2 + OpenCV |
| ② 预处理 | `1 × 3 × 640 × 640` | float32 | **4.69 MiB** | CPU（你写的代码） |
| ③ NPU 推理 | `1 × 84 × 8400` | float32 | 2.69 MiB | Ascend 310B4 |
| ④ 后处理 | `N × 4` | float32 | 几百字节 | CPU |
| ⑤ 呈现 | JPEG 字节流 | uint8 | ~80 KB | CPU |

**注意一个反直觉的数字**：预处理后的输入（4.69 MiB）比原始采集（2.64 MiB）**还大 1.78 倍**。

原因：像素数量少了（409,600 vs 921,600，只剩 44%），但每个像素从 1 字节变成 4 字节 float32（×4）。`0.444 × 4 = 1.78`。

## 2. 逐阶段拆解

### ① 采集：`/dev/video0` 不是文件

摄像头在 Linux 里是**字符设备**，通过 V4L2（Video for Linux 2）接口访问。OpenCV 的 `VideoCapture` 是这个接口的封装。

```python
cap = cv2.VideoCapture("/dev/video0", cv2.CAP_V4L2)
cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*"MJPG"))
cap.set(cv2.CAP_PROP_FRAME_WIDTH, 1280)
cap.set(cv2.CAP_PROP_FRAME_HEIGHT, 720)
cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)   # 关键
```

**为什么用 MJPG 而不是原始位图？**

1280×720×3 未压缩 = 2.64 MiB/帧。30 fps 就是 79 MiB/s，超出 USB 2.0 的实际带宽（约 35–40 MiB/s）。所以让摄像头**硬件内压缩成 MJPEG**，带宽降到约 2 MiB/s，OpenCV 再解压。

代价是多了一次编解码开销，但这是 USB 摄像头的通用做法。

**`BUFFERSIZE = 1` 是在解决什么问题？**

V4L2 驱动默认维护一个 4 帧的环形缓冲。你的程序如果处理得慢，`read()` 拿到的是队列里最旧的那帧，延迟越积越大——你会看到"慢动作"。

设成 1 之后，驱动只保留最新一帧，读到的一定是"现在"。这对实时检测是必须的，对录像反而不能用（会丢帧）。

**返回值的坑**：`cap.read()` 返回 `(ret, frame)`。`ret` 为 False 时 `frame` 可能是 `None`，直接往下传会崩。代码里那个 `if not ok or frame is None` 不是多余的。

**通道顺序**：`frame` 是 **BGR** 不是 RGB。这是 OpenCV 为了兼容 1990 年代的摄像头驱动留下的历史包袱，至今没改。

### ② 预处理：四步变换，一步都不能少

```python
canvas, scale, (left, top) = letterbox_yolov8(frame, 640)   # 几何
x = preprocess_yolov8(canvas)                               # 数值
x = x[None, ...]                                            # 加 batch 维
```

四个动作：

| 动作 | 从 | 到 | 不做会怎样 |
|---|---|---|---|
| **letterbox** | 1280×720 | 640×640 | 比例失真，框飘、置信度掉 |
| **BGR → RGB** | B,G,R | R,G,B | 红蓝互换，肤色变蓝，检测变差 |
| **÷ 255** | [0,255] | [0,1] | 输入量纲大 255 倍，模型饱和输出乱码 |
| **HWC → CHW** | (H,W,C) | (C,H,W) | 内存布局错，pyACL 报错或结果错乱 |
| **ascontiguousarray** | 转置视图 | 连续内存 | 视图内存不连续，DMA 传参出错 |

#### letterbox 的确切几何

```
原图 1280×720
  scale = min(640/720, 640/1280) = min(0.889, 0.5) = 0.5
  → 缩放到 640 × 360

画布 640×640
  pad_w = 640 - 640 = 0      → left = 0
  pad_h = 640 - 360 = 280    → top  = 140
  → 上下各填 140 行灰边（BGR 114,114,114）
```

**为什么取 `min` 而不是分别缩放？** 取 `min` 保证整个画面能塞进 640×640（不裁切）。如果取 `max`，就是"填满并裁切"，会丢掉边缘的人。

**为什么填充色是 114？** ultralytics 的约定值，约等于中灰。模型训练时见的就是这个填充色，换成纯黑会让边缘区域的特征分布略有偏差。

#### `scale` 和 `(left, top)` 是整个系统最脆弱的地方

这两个数是**连接两套坐标系的唯一凭据**。它们由输入分辨率决定，一旦你改了 `--width/--height` 却没重新算，框就会整体偏移并缩放错误。

### ③ NPU 推理：OM 是编译期固化的

```python
session = InferSession(0, "yolov8n.om")    # 0 = device_id
out = session.infer([x])[0]
```

**`0` 是 NPU 设备号**。板子只有一颗 310B4，所以是 0。多卡场景才需要改。

**OM 的输入输出形状在编译时就写死了。** ATC 命令里的 `--input_shape=images:1,3,640,640` 不是建议，是合同。想改形状必须重新转换：

```bash
atc --model=yolov8n.onnx --framework=5 --output=yolov8n \
    --input_format=NCHW --input_shape=images:1,3,640,640 \
    --soc_version=Ascend310B4
```

**加载成本 vs 边际成本**——这个概念很重要：

| | 耗时 | 说明 |
|---|---|---|
| `InferSession(...)` 加载模型 | ~1.2 秒 | 一次性，把权重和计算图搬进 NPU |
| `session.infer([x])` 单次 | 26.5 ms | 只做 host→device 数据搬运 + 计算 |

所以**绝不能把模型加载放进循环里**。实验一那个反面教材就是每条样本起一次子进程，56,962 次 × 1.2 秒 ≈ 19 小时，而真正的计算只占 12 秒。

---

### ④ 后处理：8400 → 个位数

输出 `1×84×8400` 的结构（见另图）：84 = 4 个框参数 + 80 个类别分数，8400 = 80² + 40² + 20² 三个尺度的网格总数。

```python
preds = output[0].T                    # (84,8400) → (8400,84)
cls_ids  = preds[:, 4:].argmax(1)      # 每行最可能的类别
cls_conf = preds[:, 4:].max(1)         # 对应的置信度
keep = (cls_conf >= 0.40) & (cls_ids == 0)   # 阈值 + 只留 person
```

**为什么 `person_only` 是 `cls_ids == 0`？** COCO 数据集的 80 个类里，第 0 类就是 person。这个顺序不能猜，必须查 COCO 的类别定义。

**中心点式转角点式**：模型输出的是 `(cx, cy, w, h)`，画框需要 `(x1, y1, x2, y2)`：

```
x1 = cx - w/2    y1 = cy - h/2
x2 = cx + w/2    y2 = cy + h/2
```

**NMS 在解决什么**：同一个目标会被相邻的多个网格同时检出，产生一堆重叠框。NMS 按分数从高到低遍历，把与已选框 IoU > 0.45 的都丢掉。`0.45` 这个阈值就是"多相似算重复"。

#### 坐标反变换：把框还回原图

```python
x1 = (b[0] - left) / scale
y1 = (b[1] - top)  / scale
x2 = (b[2] - left) / scale
y2 = (b[3] - top)  / scale
```

**顺序不能反**：先减 pad，再除 scale。

数值验证（`left=0, top=140, scale=0.5`）：

| 画布坐标 | 计算 | 原图坐标 |
|---|---|---|
| x=200 | (200-0)/0.5 | 400 |
| y=300 | (300-140)/0.5 | 320 |
| x=400 | (400-0)/0.5 | 800 |
| y=500 | (500-140)/0.5 | 720 |

结果 `[400, 320, 800, 720]`，正好落在 1280×720 内。如果漏掉 `-140`，框会整体下移 280 像素——这就是"框明明在人身上，画出来却偏到下面"的典型症状。

---

### ⑤ 呈现：注意画在哪张图上

```python
cv2.rectangle(frame, ...)      # 画在 1280×720 原图上，不是 640 画布
ok, buf = cv2.imencode(".jpg", frame, [IMWRITE_JPEG_QUALITY, 75])
```

这里有个容易混淆的点：**框的坐标是原图的，所以要画在原图上**。如果你先画在 640 画布上再放大，线条会变粗且位置有偏移。

JPEG 质量 75 是画质/体积的平衡点，1280×720 约 80 KB。质量调到 95 会变成 300 KB，而 MJPEG 是逐帧推送的，带宽和编码时间都会涨 3 倍。

## 3. 数据契约破坏实验

想知道每一步为什么必须存在，最快的办法是**故意做错，观察后果**。这张表是逐个验证过的：

| 破坏方式 | 现象 | 根本原因 |
|---|---|---|
| 直接 `resize` 到 640×640 | 框偏移、置信度整体下降 0.1~0.2 | 长宽比从 1.78 变 1.0，人体比例失真 |
| 忘记减 `left/top` | 框整体下移 280 px | 坐标系错位 |
| `scale` 用了 `max` 而不是 `min` | 画面被裁切，边缘的人检测不到 | 填充策略不一致 |
| BGR 不转 RGB | 红色物体识别率骤降，肤色异常 | 通道互换 |
| 不 `÷ 255` | 输出全是接近 0 的分数，或满屏乱框 | 输入量纲是训练时的 255 倍 |
| 不转 CHW | pyACL 报形状错误，或框完全错乱 | 内存按通道优先解释错了 |
| 忘 `ascontiguousarray` | 偶发形状错误 / 结果不稳定 | 转置后是视图，内存不连续 |
| `--size` 改成 512 不重编译 OM | `input shape mismatch` 直接报错 | OM 形状编译期固化 |
| 漏掉 `person_only` | 出现椅子、瓶子、手提包的框 | 80 类全输出 |
| 置信度阈值 0.9 | 远处的人全漏 | 小目标置信度本来就低 |

## 4. 跨平台契约差异：同一模型，两套规矩

这是最值得研究的一点。**预处理不是模型的属性，是"模型 + 推理后端"组合的属性。**

同一个 `yolov8n.onnx`，在两个平台上要求完全不同：

| | Ascend 310B4（本项目） | RK3588 / RKNN |
|---|---|---|
| 归一化在哪里做 | Python 里 `÷255` | RKNN config 设 `mean=0, std=255`，**运行时内部做** |
| Python 端应传 | `float32`，值域 [0,1] | `uint8`，值域 [0,255] |
| 如果弄错 | — | **双重归一化**，模型收到 [0, 1/255]，检测完全失效 |

`utils/preprocess.py` 里为此专门留了两个函数：

```python
def preprocess_yolov8(canvas):        # Ascend：RGB + /255 + CHW float32
def preprocess_yolov8_uint8(canvas):  # RKNN：RGB + CHW uint8，绝不 /255
```

**教训**：换推理后端时，第一个要重新确认的不是模型文件，而是"归一化到底谁做、在哪里做"。这是我在实验二踩过的同类坑——阈值 0.97 在两种输出尺度下含义完全不同。

## 5. 怎么验证契约是对的

四种方法，从便宜到严谨：

### 方法一：打印中间张量（最实用）

在预处理和推理之间插一行：

```python
print(x.shape, x.dtype, x.min(), x.max(), x.mean())
# 期望: (1,3,640,640) float32 0.0 1.0 ~0.4x
```

如果 `max` 是 255 而不是 1，就是漏了 `÷255`。如果 `min` 是负数，说明误加了归一化。

### 方法二：同图跨平台比对

同一张图，PC 上 `onnxruntime` 跑一遍，板上 OM 跑一遍，比输出张量：

```python
diff = np.abs(out_onnx - out_om).max()
# 期望 < 1e-3
```

实验一验证过这条链路（diff ≈ 0，ONNX 与 OM 结果一致率 99.998%）。

### 方法三：已知答案的图

`bus.jpg` 这张图的标准答案是 4 个人。任何改动后先用它测——少于 4 个或框位置明显偏移，说明契约被破坏了。

### 方法四：极端输入测试

- 全 0 输入 → 应该输出 **0 个框**
- 全 1 输入 → 也应该接近 0 个框

如果全 0 输入还能框出一堆东西，说明预处理或解码有严重问题（比如形状错位把权重当像素读了）。

## 6. 性能归因：26.5 ms 只占整环 40%

实测端到端 72 ms / 13.8 fps，但 NPU 推理只要 26.5 ms。剩下的时间在哪：

| 环节 | 耗时 | 占比 |
|---|---|---|
| 采集等待（等摄像头出下一帧） | ~33 ms | 46% |
| letterbox + 预处理 | ~4 ms | 6% |
| **NPU 推理** | **26.5 ms** | **37%** |
| 后处理解码 + NMS | ~3 ms | 4% |
| 画框 + JPEG 编码 | ~5 ms | 7% |

**关键观察：最大的一块是"等摄像头"，不是计算。**

所以想提帧率，优化的优先级是：

1. **多线程**：采集一个线程、推理一个线程，用"最新帧"策略，能把等待时间与其他环节重叠 → 理论 25 fps
2. **降低采集分辨率**：1280×720 → 960×540，采集和编码都快 → 但注意 `scale` 会变，反变换要跟着改
3. **降 JPEG 质量**：75 → 60，编码省 2 ms
4. 推理本身：换量化模型或更小的输入尺寸，但要重新编译 OM

**不要做的事**：把推理线程从 1 加到 4。NPU 只有一颗，多个线程抢同一个会话只会互相阻塞，实测反而更慢。

## 7. 想深入研究的切入点

按难度排序：

1. **改输入尺寸**：把 OM 重编译成 `1×3×512×512`，观察精度和延迟的 trade-off。要同步改 `--size` 和 letterbox 的 `scale`。
2. **换量化精度**：ATC 支持 `--precision_mode=allow_fp32_to_fp16`，对比精度损失。
3. **多线程流水线**：把采集和推理拆开，用 `queue.Queue(maxsize=1)` 只保留最新帧，实测能到多少 fps。
4. **动态 batch**：ATC 支持 `--dynamic_batch_size`，一次推理多帧。摄像头场景用不上，但视频文件批处理有用。
5. **AIPP 硬件预处理**：Ascend 支持在 NPU 内部做色域转换和归一化，可以把 CPU 的 4 ms 省掉。需要用 `--insert_op_conf` 配 AIPP 文件。
6. **换检测模型**：yolov8s/m 的 mAP 更高但更慢，在 310B4 上跑一下看拐点。

## 附：完整链路一行摘要

```python
frame = cap.read()                                    # (720,1280,3) uint8 BGR
canvas, scale, (left, top) = letterbox(frame, 640)    # (640,640,3)  uint8 BGR + 灰边
x = preprocess(canvas)[None]                          # (1,3,640,640) float32 RGB
out = session.infer([x])[0]                           # (1,84,8400)  float32
boxes, scores, ids = decode(out, 0.40, 0.45)          # (N,4) 画布坐标 xyxy
boxes = (boxes - [left,top,left,top]) / scale         # (N,4) 原图坐标
cv2.rectangle(frame, ...)                             # 画在原图上
```

八行代码，就是模型与摄像头之间的全部关系。
